## Summary

The Cooker suite has about 1,130 GoogleTest cases in 119 test files and two
Python CLI tests. They are built into 40 executables. Most individual tests are
good, but five problems make the suite slow to work in and hard to trust:

1. **Unit and functional tests are mixed in the same executables.** CTest
   registers one test per executable, so there is no way to run "just the fast
   tests". A hang or flake in one threaded test fails every unit test in the same
   executable. ([F-01](#f-01))
2. **Several tests can hang forever or crash** instead of failing:
   - unbounded `latch.wait()`
   - `EXPECT` checks followed by a dereference of the checked value
   - `sleep_for` used as synchronisation
   - two tests named `DISABLED...` without the underscore, which therefore still
     run and point at `F:\` paths.

   ([F-02](#f-02)–[F-05](#f-05))

3. **About 3,000 lines of helper code are copied.** The JSON-schema harness has
   11 copies, there are about 50 hand-rolled temp-directory setups, 15
   byte-reader copies and 11 submit-and-wait helpers. ([F-06](#f-06))
4. **Test files do not map predictably to source files.** For example,
   `ImportJobLifetime_test.cpp` mostly tests registries, `LooseCookedWriter`
   tests live under `Loose/`, and the Inspector tests live under `Import/`.
   ([F-08](#f-08))
5. **A few files are too large to review**, for example
   `ScriptImportJob_test.cpp` at 3,445 lines and `PakWriter_test.cpp` at 1,692
   lines. ([F-09](#f-09))

The plan fixes these in seven phases. Each phase can be merged on its own and
proves itself by **not losing a single test** (see [CT-0](#ct-0-baseline)).
It adds:

- three tiers, `unit`, `functional` and `gpu`, as CTest labels
- a mechanical rule that maps a source file to its test file
- one small shared test-support library

It does not rewrite tests that already work, and it does not introduce a test
framework. It also does not add tests that inspect source code: layout rules are
enforced by review, not automation ([D-08](#6-decisions)).

## 2. Target design

### 2.1 Test tiers

Every test file belongs to exactly one tier, and every executable contains files
of exactly one tier. Decide a file's tier with this procedure. The first "yes"
wins, and **if in doubt, choose the slower tier**.

| #   | Question (about _any_ test in the file)                                                                                        | If yes →   |
| --- | ------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| 1   | Does it create a graphics device or need a real GPU?                                                                           | **gpu**    |
| 2   | Does it write files or create directories (including temp dirs)?                                                               | functional |
| 3   | Does it read a model or image asset from `Test/Assets/`?                                                                       | functional |
| 4   | Does it start threads: `co::ThreadPool`, `ImportEventLoop` with workers, `AsyncImportService`, `AsyncImporter`, `std::thread`? | functional |
| 5   | Does it start a subprocess?                                                                                                    | functional |
| –   | Otherwise (in-memory, deterministic, single thread; reading a checked-in **JSON schema** through `SchemaPath()` is allowed)    | **unit**   |

If a file mixes tiers, split it so that the unit tests move to `X_test.cpp` and
the rest move to `X_functional_test.cpp`. [§3](#3-file-mapping) lists every
split.

The **gpu** tier is empty today and is only reserved. When a Cooker test needs a
device (for example a GPU BC7 path), give it `X_gpu_test.cpp` and a `*.Gpu.Tests`
executable registered with the `GPU` option. That option already adds the
`oxygen_gpu` resource lock, and after CT-1 it also adds the `gpu` label. Do not
create empty GPU executables.

### 2.2 Directory layout and the mapping rule

**Rule (mechanical).** A test for source file `Cooker/<Dir>/<Stem>.{h,cpp}` lives in
`Cooker/Test/<Dir'>/<Stem>[_<aspect>][_functional|_gpu]_test.cpp`, where
`<Dir'>` is chosen as follows:


### 2.8 Module boundary: what a Cooker test may use

The Cooker depends on Data and Content. A Cooker test checks **Cooker output**:
cooked files, pak bytes, catalogs, manifests, reports and diagnostics. It may
read that output back with:

- Cooker's own readers: `lc::Inspection`, `lc::ValidateRoot(…, IntegrityCheck::kFull)`
  (this also verifies content hashes), and the Pak plan, catalog and manifest
  types.
- Data's format types (`data::pak::*` descriptors, `PakCatalog`,
  `AssetReferences`), copied out with `memcpy` as the rules require.
- Content's **stateless public format readers**:
  - `content::PakFile`: directory, `ReadAssetReferences`, resource tables, data
    regions, `Catalog()`
  - loader functions called with `LoaderContext { .parse_only = true }`, which
    is the existing pattern in `AsyncGltfImporter_test.cpp:85` and
    `GeometryDescriptorImportJob_test.cpp:313-334`.

A Cooker test must **not**:

- include or call `content::internal::*`
- construct a `content::AssetLoader`. It needs the Engine-internal
  `engine::internal::EngineTagFactory`, and it tests runtime orchestration:
  mounting, precedence, tombstones, load scopes, publication and dependency
  collection.
- assert anything a Content function computes from bytes the Cooker test has
  already proven correct.

Behaviour that sits on the Content side of this line is tested in Content, with
Content's fixtures. End-to-end acceptance (sources cooked, packed and loaded by
the real runtime) is already exercised by the Examples content pipeline:
`Examples/Content/import_models`, `cook_scenes` (including the
`physics_domains` scene with its physics sidecar) and `pak_content`, consumed
by `RenderScene` and `DemoShell`. No new example scenario is needed, because
every check in [E.6](#e6-cross-module-assertions-d-07) can be written inside a
single module.

## 4. Implementation plan

General rules for every phase:

- **One PR per phase**, or per slice where a phase lists slices.
- **Do not change test behaviour while moving files.** A move commit contains only
  `git mv` and CMake changes, so reviewers can see it is mechanical. Content
  edits go in a separate commit.
- **Prove nothing was lost.** After every slice, run the inventory diff from
  [Appendix D](#appendix-d-test-inventory-diff). Every removed or renamed test
  name must appear in the slice's rename list in the PR description.
- Run `oxyformat` on changed C++ before building, and `oxytidy` before asking
  for review. Clear all warnings in touched files ([RULES](../../../../design/oxygen/RULES.md)).
- Build only the Cooker test targets (`cmake --build <build> --target <exe>`),
  not the whole engine. Then run them with `ctest -R "^Oxygen\.Cooker\."`.
- Commit only after review approval.

## 5. GoogleTest rules for this suite

These apply to all new and touched code. Reviewers check them.

1. **One behaviour per test.** If the name needs "And", split it.
2. **Use `ASSERT_*` when continuing would crash or be meaningless.** That covers
   optional/pointer access, container indexing and `report.success` before reading
   outputs. Use `EXPECT_*` for independent checks. Never dereference something
   that was only `EXPECT`ed.
3. **Write helpers so failure is explicit.** A helper either returns a value
   (`std::optional`, or throws `std::runtime_error` with context, which
   GoogleTest reports as a failure), or is `void` and uses `ASSERT_*`, called
   through `ASSERT_NO_FATAL_FAILURE(Helper())`.
4. **Fixtures hold shared setup.** Use plain `TEST` when there is no state, and
   no empty fixture classes. Use one suite per file.
5. **Use `TEST_P` for tables of inputs**, always with a name generator. Use a
   `for` loop with `SCOPED_TRACE` only for 2–3 inline cases.
6. **Name death-test suites `…DeathTest`.**
7. **Use matchers** (`HasSubstr`, `ElementsAre`, `Contains`, `Field`,
   `Optional`) rather than `EXPECT_TRUE(<expression>)`, because matchers print
   useful failure messages.
8. **Keep tests hermetic.**
   - Write only inside `TempDir()`.
   - Do not use fixed temp names, the working directory, or machine-specific
     absolute paths.
   - Find assets only through `ModelPath`/`SchemaPath`.
9. **Do not use sleeps.** Synchronise with latches, promises or gates, and
   always bound waits (`wait_for`) so a bug fails fast instead of hanging.
10. **Use `GTEST_SKIP()` only for a missing environment capability** (for
    example no GPU), always with a message. Never skip because a checked-in
    file is missing. Never use `DISABLED_` without a tracking ID in a comment.
11. **Test observable behaviour**, not private call sequences or another
    module's internals.
12. **Write comments that explain why**, not what the name already says. Do not
    use plan section numbers.
13. **Wrap everything in an anonymous namespace**, as the suite already does.

## Appendix C: `Test/README.md` draft

```markdown
# Cooker tests

## Run

| What                     | Command                                                                  |
| ------------------------ | ------------------------------------------------------------------------ |
| Fast loop (unit)         | `ctest --test-dir <build> -C Debug -R "^Oxygen\.Cooker\." -L unit`       |
| Before a PR (functional) | `ctest --test-dir <build> -C Debug -R "^Oxygen\.Cooker\." -L functional` |
| One executable, filtered | `Oxygen.Cooker.Import.Unit.Tests --gtest_filter=TextureCooker*`          |

## Tiers

`unit` means in-memory, single thread, no writes and no model assets. Reading
checked-in schemas is allowed. `functional` means files, threads, assets,
subprocesses or several components. `gpu` means a real device is needed (none
today). The decision procedure is in
design/content-pipeline/cooker-test-suite-plan.md §2.1.

## Where is the test for X?

Source `Cooker/<Dir>/<Stem>.cpp` →
`Test/<Dir without Internal/>/<Stem>[_aspect][_functional|_gpu]_test.cpp`.
`Jobs/`, `Pipelines/`, `Emitters/` and `Schemas/` keep their subdirectory.
Tool tests live in `Tools/<Tool>/Test/`. Cross-area workflows live in
`Test/Scenarios/`.
Every test file names its sources on a `// Covers:` line. To find the tests for
a source file: `rg "Covers:.*<Stem>" Test Tools`.

## Adding a test

1. Put it in the file the rule gives you. Create the file if it is missing.
2. Add the file to the matching `oxygen_cooker_test(<Area> <TIER> …)` call in
   `CMakeLists.txt`.
3. Use the helpers in `Support/`: `TempDirTest`, `ModelPath`, `SchemaPath`,
   `SubmitAndWait`, `ImportServiceTest`, `ReadBytes`/`WriteText`,
   `HasDiagnosticCode`. Do not copy them.
4. Follow the GoogleTest rules in the plan (§5): one behaviour per test, ASSERT
   before dereferencing, no sleeps, no fixed paths.
```

## Appendix D: Test inventory diff

Requires Python 3.10+. Save this as a local script outside the repository (for example in your build
directory), not in Git. Run it after each slice.

```python
# list_cooker_tests.py <build-bin-dir> <out.txt>
import pathlib, subprocess, sys

bin_dir, out = pathlib.Path(sys.argv[1]), pathlib.Path(sys.argv[2])
names = []
for exe in sorted(bin_dir.glob("Oxygen.Cooker.*.Tests*")):
    if exe.suffix not in ("", ".exe"):
        continue
    listing = subprocess.run([str(exe), "--gtest_list_tests"], capture_output=True,
                             text=True, check=True).stdout
    suite = ""
    for line in listing.splitlines():
        text = line.split("#")[0].rstrip()  # drop "# GetParam() = ..." comments
        if not text.strip():
            continue
        if not line.startswith(" "):
            suite = text.strip()            # "Suite." (or "Prefix/Suite.")
        else:
            names.append(suite + text.strip())
out.write_text("\n".join(sorted(set(names))) + "\n")
print(f"{len(names)} tests")
```

The comparison uses `Suite.Test` names without the executable, so moving a file
between executables doesn't produce noise. Compare with
`git diff --no-index baseline-tests.txt current-tests.txt`. Every `-` line must
be matched by a `+` line in the PR's rename list, or be one of the deliberate
deletions (CT-2.1).
